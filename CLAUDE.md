## Project

Research home for the **model-internals safety** line: safety research that operates INSIDE model parameters — training-time interventions (safety fine-tuning, unlearning) and parameter/activation-space work (activation steering, representation-level analysis and edits). **Model-size-agnostic by design:** the pipeline is the same for a 1B and a 70B; small open models are the default experimental substrate (cheaper runs, more seeds). **A FIFTH decision was settled 2026-08-06 and it is the one a session building I4/I5/I6 needs: §3.5, where WRITE-side instruments plug in.** Every instrument up to I3 *reads* activations we captured, so it runs inside the family loop; the causal instruments *write* to the model, and that is a different shape — which is why `models/interventions.py` and `measurements/causal_license.py` sat built-and-unreachable for a day while I1–I3 were wired in an afternoon. **Causal licensing is a MODEL-level gate, not a rung-level instrument:** the direction is fit on the plain contrast sets, is identical for every rung, and gates which direction the downstream reads may use at all (TODO 28, from Arditi et al., NeurIPS 2024) — so it runs once between the plain captures and the family loop. ## Conventions

- **Package manager is `uv`** (global law); `uv.lock` is committed. No application frameworks, CLI structure, or trackers assumed before discussion — whether this project ever needs one is deferred until the phase-0 pilot shows the real run shapes (`text_docs/project_structure.md` §7.3).
- **Artifact layout:** `outputs/activations/` is a capture cache reusable across analyses; `outputs/runs/<phase>/<model>/<run_name>/` holds one dir per run with its `results.json` provenance record. Both gitignored; both defined in `src/internals_safety/paths.py`.
- **LLM provider layer:** the `llm_utils` base package as a pinned git dep by tag (family convention; never vendor a copy) — pinned at `v5.0.0`, the same tag as the guardrail sibling, so judge behaviour matches across the family.
- **API keys** reach the process from the secret manager at launch, via the gitignored repo-root `run` wrapper and its pointer map. Nothing vault-shaped is ever committed; no plaintext key touches disk. The same wrapper is the cluster path.
- **Experiment-run approval gate (family rule, owner 2026-07-22):** training and intervention runs are heavy — BEFORE launching ANY run, report an explicit estimate of (1) GPU count + type, (2) money ($), and (3) wall-clock time, and get the owner's explicit go.
- **Cluster runs go through a committed PRESET, never a hand-typed flag string (settled 2026-08-07).** `conf/experiment/<name>.yaml` declares the run; `scripts/submit.py <preset>` prints it and submits NOTHING without `--submit`; `ops/run.sbatch` is the one generic launcher. The three-command loop is `submit.py <preset>` → `cost_model.py --preset <preset>` → the owner's go → `--submit`. **Do not write a new `*.sbatch` per experiment** — that is what this replaced, and two of the three it replaced existed only on the cluster, never in git. Two schema properties are load-bearing and must not be relaxed: the schema is CLOSED (no preset may carry a `measurements.yaml` knob — enforced by `tests/test_presets.py`), and `gates:` is REQUIRED, so a job cannot be constructed until *what would I build differently depending on the result?* is answered in a committed file. Local work keeps argparse.
- **⚠️ A run must be a GATE, not a measurement, until the instrument roster is complete (owner defect report 2026-08-06; problem report filed as science TODO item 18, science rules on the general law).** The test, applied BEFORE launch: *what would I build differently depending on the result?* No answer means the run gates nothing, and a run that gates nothing waits until the instruments are done. This is **not** the S6b grounding rule and S6b does not cover it — every instrument can be grounded and a session can still choose a non-blocking run over continuing the build, which is what happened on 2026-08-05: the AS-6 phase-1 sweep and the comprehension band both ran after the gating question was already answered (`4453bed`), and the instrument build plan naming what to build (`00da340`) arrived after both. Cost: thirteen instrument-repair commits in one day all downstream of runs, every quantitative map from both runs revised at least once, and a roster that **as of 2026-08-06** still had I4/I5 unbuilt, I6 partial, six modules wired to zero scripts, and 4 of 9 mandatory controls missing. *(State as of 2026-08-07, from `build_status.py` — do not re-sweep by hand: I0–I3, I5, I6 all complete, control battery 7/7, and **I4 is the single remaining roster item**. Its unbuilt half is deliberately gated on the SAE pre-gate, which needs the 8B Base arm — cluster work. The rule stands; what has changed is that finishing the roster now REQUIRES a run rather than being blocked by one.)* **The empirical basis for the rule, from this repo's own data:** the pilot's GATE answer ((B) is populated) survived every subsequent instrument fix unchanged, while every quantitative MAP from the same runs was revised — a go/no-go is robust to instrument quality in a way a measurement is not.
- **Compute options — this repo has been designed around ONE of three, and that is now a live question (noted 2026-08-05).** Every design decision here assumes **NURC/Explorer**: free, but `normal` QOS = **1 GPU per job, 8 h wall, 4 concurrent, multi-GPU never schedules**. **The `gpu` partition's own QOS is the binding one, and it has TWO caps, read from `sacctmgr` 2026-08-07: `MaxJobsPU=4` (running) and `MaxSubmitJobsPU=8` (running + pending).** Three consequences that cost a submission before they were known: the submit cap binds while jobs merely sit PENDING, so a queued batch blocks later submissions; **an array job consumes one submit slot PER TASK**, so a 3-task array needs 3 of the 8; and "per user" means every session and every SIBLING PROJECT sharing this login competes for the same 8 — the guardrail sibling's `vllm_*` jobs are the same Unix user, not merely the same account, and four of them leave room for four. A refusal reads `sbatch: error: QOSMaxSubmitJobPerUserLimit`. Jobs on `short` (e.g. `relicense_all`) are outside this QOS and do not count. **Check `squeue -u $USER` for the whole login, not just this project's jobs, before planning a batch.** That constraint is why phase-0 must be split across jobs by `--families`, and the pilot still **hit the wall** (Qwen killed at 8:00:26). The family also has the **xc cluster** — a shared single-node SLURM box, partition `main`, **8×A100-80GB with NO time limit** — and **AICR**. xc is not currently referenced anywhere in this repo's design, cost model or `ops/`. Canonical facts live in the devices repo `knowledge/clusters/` (`xc_cluster_properties.md`, `nurc_cluster_properties.md`, `aicr_cluster_properties.md`; moved from science 2026-08-05); the job-portability standard is `knowledge/cluster_job_standard.md` there. **Never write any cluster's host, IP, key, or a box owner's name into this repo — it is public; the sanctioned token is "xc cluster" plus a pointer to the devices repo** (owner rule 2026-07-18). Whether this project's later phases move to xc is an open owner decision, filed in TODO.
- **Cluster sync (family standard, settled 2026-08-02):** git clone/pull for committed code + rsync/scp for the gitignored ops layer (`*.sbatch`, cluster configs) + rsync-down for results — canonical: devices repo `knowledge/cluster_sync_convention.md` (moved from the science organ 2026-08-05). - **⚠️ A test fixture must model the STRICTEST real implementation, never a convenient one (settled 2026-08-07, three instances in one day).** A fixture more permissive than the real thing is not a simplification — it is a blind spot with a green checkmark, and it certifies rather than tests. The three, all found by GPU jobs dying and none by the suite: (1) `conftest.TINY_CHAT_TEMPLATE` interpolated message content RAW while Llama-3.1 renders it through `| trim` — 1001 tests green while one trailing space in one prompt of 650 killed two H200 jobs; (2) a `meta` device standing in for a second real device, where `cpu @ meta` silently succeeds, so the test passed on the code it existed to reject; (3) `PerfectSAE`, an identity round-trip on CPU, which cannot express a device asymmetry because the reconstruction *is* the input. **The check to apply to any fixture: name the strictest real implementation it stands in for, and ask what that one does which the fake does not.** A defect this rule does NOT cover: an over-permissive value in production code that stands in for nothing — the control floor's max-vs-distribution problem is n-dependence in a real estimator, and its home is `instrument_layer.md` §2.4, not here. Reaching for a fixture when the defect is in an estimator is the misread this sentence exists to prevent. Corollaries paid for the same day — verify a new guard by MUTATION and mutate the specific branch, since counts over the whole guard say nothing about one path; and a test run whose result is chained behind a filter is not a result (`pytest | grep -E "FAILED|passed" && git commit` commits on RED, because grep exits 0 on finding "FAILED"). **A PIPE HAS ITS OWN EXIT CODE, and that is the same defect wearing a different hat (fourth instance, 2026-08-07).** `cmd | tail -35; echo $?` reports *tail's* status, so `build_status.py` — which exits 1 by contract while the roster is incomplete — read as EXIT=0 and would have certified the build as done. Same day: `tail -6` hid `sbatch: error: QOSMaxSubmitJobPerUserLimit` and a submission that never happened was reported as queued. **The rule that covers all four: when a command's SUCCESS is what you are about to act on, run it unpiped and read its own status** — redirect to a file and `cat` it if the output is long. Truncation is for reading, never for deciding.
- **Two agent sessions have shared this working directory (2026-08-07) — stage explicit paths, never `git add -A`.** A blanket stage in a tree another session is mid-edit in commits its half-finished work under a message describing something else; it happened once and was caught only by the other session noticing its own changes in a foreign commit. `scripts/submit.py` guards the SLURM side (it refuses a preset already queued or running) but nothing guards the tree. Every config carries a `## Provenance` block naming the paper, its arXiv id, and its **evidence tier**; the canonical home for the whole slate is **`text_docs/shared/model_slate.md`**, and configs point there rather than growing a second table. **⚠️ THE VENUE CHECK MUST NOT BE A METADATA LOOKUP — this rule's own first application got it wrong.** The initial sweep tiered all five models **(B)** on the basis that dblp records them as CoRR only, and reported "a COLM listing for Tulu 3 was searched for specifically and NOT found". **Tulu 3 is COLM 2025** — the OpenReview PDF (`openreview.net/pdf?id=i1uGbfHHpH`) carries the "Published as a conference paper at COLM 2025" header, and so does OLMo 2. dblp and Semantic Scholar both still say CoRR.
